Zefile

Un binaire unique pour stocker, organiser et partager de gros fichiers sur un VPS. Conçu comme le successeur spirituel de File Browser : la même promesse d’installation, avec un modèle de sécurité et une API pensés dès le départ.

01Contexte

File Browser est archivé le 1er septembre 2026. Son auteur explique que le projet ne peut pas être réparé par correctifs : écrit sans modèle de sécurité ni conception d’API, il faudrait le réécrire entièrement. Les failles connues restent publiques et non corrigées.

Le besoin, lui, ne disparaît pas : exploiter les 200 Go d’un VPS pour héberger des fichiers lourds (images disque de jeux PC, archives) et y accéder à distance, là où l’offre gratuite de Google Drive plafonne à 15 Go.

Ce document spécifie un remplaçant écrit de zéro. Pas un fork : le code existant est le passif, seules les idées d’ergonomie et la liste documentée de ses vulnérabilités sont réutilisables.

1.1Le nom

Zefile — clin d’œil à l’article défini prononcé à la française. Pas un énième explorateur de fichiers : ze explorateur de fichiers.

Homonymie connue

Il existe déjà zfile, un projet de stockage auto-hébergé actif, dont le nom ne diffère que d’une lettre et se prononce presque identiquement pour un lecteur non francophone. Aucun obstacle juridique, mais une confusion à prévoir en recherche et dans les discussions communautaires. Choix assumé.

02Principes directeurs

Cinq règles qui tranchent les arbitrages, par ordre de priorité.

Pas un clone de Drive
On construit le File Browser qui aurait dû exister. Les gens qui migrent ne veulent pas de Nextcloud : ils y seraient déjà. Toute fonctionnalité qui nous en rapproche est refusée.
La légèreté est le produit
Binaire unique, démarrage instantané, empreinte mémoire au repos négligeable. Ce n’est pas une contrainte technique, c’est l’argument de vente.
L’API est publique, toujours
L’interface web ne dispose d’aucun endpoint privilégié. Deux surfaces à sécuriser, c’est une de trop — et c’est toujours celle qu’on croit interne qui reçoit le moins de contrôles.
Le système de fichiers fait foi
La base de données n’est qu’un cache de métadonnées. Un fichier déposé en SSH apparaît immédiatement. En cas de divergence, le disque gagne.
Aucune télémétrie
Aucune mesure d’usage, aucune vérification de mise à jour, aucune requête sortante non demandée par l’utilisateur. Engagement écrit dans le README et tenu — la communauté auto-hébergée y est particulièrement attentive, et c’est un engagement qu’on ne peut pas reprendre après coup.
Petit et maintenu
C’est la charge de maintenance qui a eu raison de File Browser, pas le code. Un périmètre restreint et tenu vaut mieux qu’un projet populaire abandonné.

3.5Propriété des fichiers

Les fichiers déposés via l’application ont un propriétaire, qui lui confère des droits implicites : lire, modifier, supprimer et partager ce qu’il a déposé, sans entrée ACL explicite. Sans cela, la propriété ne serait qu’une étiquette décorative, puisqu’il n’y a pas de quotas à imputer.

À la suppression d’un compte, la propriété de ses fichiers est transférée à l’administrateur ; ses entrées ACL, ses sessions, ses jetons et ses partages sont supprimés. Aucun fichier orphelin.

Tension assumée avec le principe « le disque fait foi »

La propriété est une donnée propre à l’application, stockée dans notre base et indexée par chemin, mise à jour par nos propres opérations de déplacement et de renommage. Un fichier déplacé hors de l’application — en SSH par exemple — laisse un enregistrement orphelin, ramassé périodiquement ; le fichier retombe alors sur les seules règles ACL. C’est le prix du principe, et il est accepté.

04Architecture

4.1Deux origines HTTP, un seul binaire

C’est la décision structurante du projet, et la seule qui soit irréversible si elle est ratée.

app.domaine.tld     API + interface       cookie de session
files.domaine.tld   contenu utilisateur   aucun cookie, jamais

Tout fichier déposé par un utilisateur est du contenu potentiellement hostile. Un .html ou un .svg servi depuis l’origine de l’application, c’est une exécution de script avec accès à la session de la victime. En séparant les origines, un fichier malveillant n’a rien à voler : il n’existe aucune session sur files..

Comme les cookies ne franchissent pas les origines, l’accès authentifié au contenu passe par une URL signée à durée courte (HMAC, quelques minutes) délivrée par l’API. Les liens de partage portent leur propre jeton et vivent nativement sur cette origine, ce qui tombe juste pour les gestionnaires de téléchargement.

4.2Composants

API                REST, origine app, authentification par cookie ou jeton
Serveur de contenu upload / download / aperçus, origine files, sans session
Couche stockage    interface unique — implémentation locale, S3 plus tard
SQLite             métadonnées uniquement, jamais de contenu
Worker de tâches   téléchargement d'URL, extraction, empreintes, purge
Interface web      embarquée dans le binaire

4.3Source de vérité

Deux modèles étaient possibles. Indexer intégralement en base (approche Nextcloud) donne une recherche rapide et des métadonnées riches, au prix d’une désynchronisation permanente et d’un scanner — la principale source de bugs de ce projet. Lire le disque à chaque requête (approche File Browser) ne désynchronise jamais mais rend la recherche lente.

Décision

Le système de fichiers fait foi ; la base ne stocke que ce que le disque ne peut pas porter — ACL, partages, corbeille, empreintes, index de recherche — indexé par chemin. On conserve ainsi la propriété qui fait la valeur de File Browser : un fichier copié en SSH est visible immédiatement.

Tous les chemins sont relatifs à la racine de stockage unique, configurée au démarrage. C’est le modèle de File Browser, et il ne restreint rien : cantonner un invité à un sous-dossier se fait par une entrée ACL, et un disque supplémentaire se monte en sous-répertoire de la racine côté hôte. Le multi-racine serait une migration et une v2 d’API — coût accepté en échange d’une simplification partout ailleurs.

Deux invariants

Tous les jetons — sessions, API, invitations, partages — sont stockés hachés. Une fuite de la base ne donne aucun accès. Et les permissions sont un masque de bits, ce qui rend le calcul d’héritage trivial.

06Authentification

Le défaut central de File Browser est le jeton JWT auto-porteur : impossible à révoquer, toujours valide après déconnexion, encore accepté après expiration dans certains cas. C’est le point de départ de cette conception.

Décision

Aucun JWT. Des jetons opaques vérifiés en base à chaque requête. La déconnexion supprime la ligne : l’effet est immédiat et total. On obtient gratuitement la liste des sessions actives, la révocation à distance et le « déconnecter partout ».

6.1Deux mécanismes, un seul modèle d’autorisation

  • Navigateur — cookie de session HttpOnly, SameSite=Lax, Secure. Jamais de jeton dans le localStorage.
  • Client programmatique — jeton d’API en Authorization: Bearer.

Les deux se résolvent vers le même contexte utilisateur et traversent les mêmes contrôles. Un jeton ne détient jamais plus de droits que l’utilisateur qui l’a créé.

6.2Jetons d’API

Chaque utilisateur crée ses propres jetons, pour un script, une intégration ou la CI. Un jeton porte l’autorité complète du compte qui l’a créé — mêmes permissions, mêmes accès fichiers, résolus à chaque requête : modifier les droits du compte prend effet aussitôt sur ses jetons. Pas de portées : le modèle est délibérément simple, comme chez Dokploy. L’atténuation d’une fuite passe par la révocation du jeton concerné — et par le fait d’en créer un par usage — non par la restriction de ses droits.

Forme zefile_live_<aléatoire> — un préfixe explicite et non ambigu, pour que les outils de détection de secrets puissent le repérer dans un dépôt ou un journal. Seuls le haché et un préfixe court sont conservés ; la valeur complète n’est affichée qu’une fois, à la création. Chaque jeton expose sa date de dernier usage, pour repérer et révoquer ce qui traîne.

6.3Journal d’audit

Le share_access_log (§08) ne couvre que les partages. Un système multi-utilisateurs doit pouvoir répondre à « que s’est-il passé » : connexions réussies et échouées, modifications de permissions, création et révocation de jetons, suppression de comptes, suppressions définitives de fichiers.

Consultable par l’administrateur, avec une durée de conservation configurable — l’adresse IP y figure, ce qui en fait une donnée à ne pas garder indéfiniment par défaut.

6.4Divers

  • Mots de passe hachés en Argon2id.
  • TOTP à deux facteurs dès la version 1 : peu de travail, bénéfice immédiat.
  • Limitation du débit sur la connexion, par identifiant et par IP.

07Permissions

Portée du modèle

Ce système est entièrement interne à l’application : il régit les utilisateurs de l’instance, leurs groupes et les liens de partage. Il n’a aucun rapport avec les droits du système hôte — comptes du système, chmod, listes de contrôle POSIX. Le serveur accède au disque sous une identité unique, et toute l’autorisation se joue dans la couche de stockage du projet.

Masque de bits : READ, WRITE, DELETE, SHARE, MANAGE. Les sujets sont un utilisateur, un groupe, ou un lien de partage — ce dernier étant un sujet de première classe, pas un cas particulier.

7.1Résolution

Pour un chemin donné, on remonte de la racine jusqu’au chemin en accumulant les entrées applicables (celles de l’utilisateur et celles de ses groupes). La plus spécifique l’emporte. Un refus explicite prime toujours sur une autorisation héritée.

La propriété s’ajoute en amont de ce calcul : le propriétaire d’un fichier dispose implicitement de READ, WRITE, DELETE et SHARE dessus. Un refus explicite reste prioritaire, ce qui permet à l’administrateur de verrouiller un chemin même contre son déposant.

7.2Deux règles non négociables

Règle 1 — le point de contrôle

La vérification s’effectue dans la couche de stockage, jamais dans les gestionnaires HTTP. Placée dans les gestionnaires, il suffit d’oublier un endpoint pour ouvrir une brèche — c’est le mécanisme d’une bonne partie des vulnérabilités de File Browser.

Règle 2 — pas d’escalade par partage

On ne peut pas partager plus de droits qu’on n’en détient. Un utilisateur en lecture seule ne peut pas créer un lien en écriture.

08Partage par lien

Contrainte fondatrice : un lien doit être téléchargeable par un gestionnaire de téléchargement type IDM. Ces clients n’exécutent pas de JavaScript, ne gèrent pas de cookies, et ouvrent 8 à 16 connexions parallèles. Cela impose une forme précise.

https://files.domaine.tld/s/<jeton>/Nom-Du-Fichier.iso
                             │              └─ détermine le nom du fichier
                             └───────────────── capacité, vérifiée en base

Aucune page intermédiaire, aucune redirection JavaScript : du point de vue HTTP, le lien se comporte comme un fichier statique. Le jeton est porté par l’URL et non par un cookie — c’est un modèle de capacité assumé : qui détient le lien peut lire.

8.1Garde-fous

  • Jeton vérifié en base à chaque requête, donc révocable immédiatement. Jamais auto-porteur.
  • Expiration paramétrable, sans plafond imposé, option « n’expire jamais » assumée.
  • Écran listant tous les partages actifs avec leur date de dernier accès. Le filet de sécurité est la visibilité, pas la contrainte.
  • Limitation de débit par IP — sans elle, un lien qui fuite transforme le VPS en CDN public.

8.2Trois pièges à traiter explicitement

Piège 1 — le décompte des téléchargements

Compter les requêtes HTTP est faux : un client multi-connexions en consomme seize d’un coup et fait sauter la limite instantanément. Il faut compter les téléchargements distincts — fenêtre glissante par IP, requêtes Range regroupées en une session logique.

Piège 2 — mot de passe et gestionnaires de téléchargement

Vérifier un mot de passe suppose un aller-retour qu’un client comme IDM ne fera pas. D’où deux natures de liens : le lien protégé passe par l’interface web, qui délivre ensuite une URL directe temporaire ; le lien direct n’a pas de mot de passe et tient sa sécurité de l’imprévisibilité du jeton et de son expiration.

Piège 3 — la qualité de l’implémentation de Range

C’est ce qui fait fonctionner le multi-connexions et la reprise. Sur des fichiers de plusieurs dizaines de Go, une implémentation approximative se voit immédiatement. À couvrir par des tests dédiés : plages ouvertes, plages suffixes, plages invalides, requêtes concurrentes sur un même fichier.

09Stockage & sécurité des chemins

Toute la surface de traversée de répertoire — ../, liens symboliques, liens durs, séparateurs Windows, encodages Unicode équivalents — est traitée en un seul endroit : la couche de stockage.

Décision

Utilisation de os.Root, qui contraint toutes les opérations à un sous-arbre au niveau de l’appel système. Conçu exactement pour ce problème, il élimine une classe entière de bugs par construction plutôt que par vigilance.

L’interface de stockage reste volontairement générique — Stat, List, Open, Create, Move, Remove, MkDir — pour accueillir plus tard WebDAV et S3 sans refonte. Les vérifications ACL sont appliquées à ce niveau, pas au-dessus.

9.1Aperçus : une décision radicale

Le principe est net : le serveur ne parse jamais un document. Tout s’appuie sur les rendus natifs du navigateur — images, vidéo (avec navigation temporelle), audio, et PDF dans une iframe cloisonnée servie par l’origine de contenu — tandis que le texte, code et Markdown compris, est montré en source, sans coloration ni rendu. Aucun analyseur de format dans le backend, donc aucune vulnérabilité de bibliothèque à suivre — précisément la catégorie de problèmes que l’auteur de File Browser a renoncé à corriger.

Seul renoncement : pas de vignette de première page en vue grille pour les PDF. On affiche une icône. Les vignettes d’images et de vidéos, elles, sont générées côté serveur par des processus séparés, sans privilèges et avec des limites de ressources.

9.2Tâches serveur : deux surfaces d’attaque

Les fonctionnalités de §3.2 font agir le serveur pour le compte de l’utilisateur. Chacune ouvre une brèche classique qu’il faut traiter explicitement.

Téléchargement depuis une URL — falsification de requête serveur

Une URL fournie par l’utilisateur permet de faire émettre au serveur des requêtes vers son propre réseau : services internes, autres conteneurs, et surtout l’endpoint de métadonnées des hébergeurs cloud, qui délivre des identifiants. Parades cumulées : schémas limités à http et https, résolution DNS effectuée avant la connexion puis vérification que l’adresse obtenue n’appartient à aucune plage privée, locale ou de lien-local, et revalidation à chaque redirection — sans quoi une redirection ramène tranquillement vers une adresse interne. S’y ajoutent une taille maximale et un délai d’expiration.

Extraction d’archive — traversée et bombe de décompression

Une entrée d’archive nommée ../../etc/passwd écrit hors du dossier cible : chaque nom d’entrée est normalisé et vérifié comme un chemin utilisateur ordinaire, via la même couche de stockage. Les liens symboliques contenus dans l’archive sont ignorés. Une archive de quelques mégaoctets pouvant se développer en téraoctets, on plafonne le taux de compression, la taille totale décompressée et le nombre d’entrées, avec abandon dès dépassement.

9.3Normalisation Unicode des noms

Le §09 traite jusqu’ici la normalisation des chemins sous l’angle de la sécurité. Elle pose aussi un problème de correction, distinct et tout aussi structurant.

Un caractère accentué s’écrit de deux manières en Unicode : composée (un seul point de code) ou décomposée (lettre + accent). macOS écrit historiquement les noms sous forme décomposée, Linux conserve ce qu’on lui donne. Deux fichiers dont le nom paraît identique à l’écran peuvent donc porter des octets différents.

Décision

Les noms sont normalisés en forme composée pour tout ce qui sert de clé : entrées acl, file_owners, shares, index de recherche et comparaisons. La forme réellement présente sur le disque est conservée pour les appels système, jamais pour l’indexation. Sans cette règle, une recherche ne trouve pas un fichier existant, deux entrées semblent identiques sans l’être, et une règle de permission cesse de s’appliquer parce que le chemin ne correspond plus.

Ambiguïté : refuser plutôt que deviner

Deux entrées d’un même dossier peuvent se normaliser vers la même clé — deux orthographes d’un même nom accentué. Choisir l’une des deux reviendrait à agir sur un fichier que l’appelant n’a pas désigné, ce qui est inacceptable pour une suppression. L’opération échoue explicitement. Le cas est rare mais atteignable : il suffit de deux marques diacritiques écrites dans l’ordre inverse. Décidé en implémentant le §14 lot 1.2.

S’y ajoutent la sensibilité à la casse — différente entre systèmes de fichiers — et les caractères interdits selon les plateformes, à traiter au même endroit : la couche de stockage, seule autorité sur la forme d’un chemin.

9.4Saturation du disque

Conséquence directe de l’absence de quotas : le disque finira par se remplir. Le danger n’est pas l’envoi qui échoue — c’est attendu et récupérable — mais que SQLite ne puisse plus écrire. Sans espace, plus de session, plus de connexion possible : l’application est entièrement hors service alors que les fichiers sont intacts et que l’administrateur ne peut même plus se connecter pour faire du ménage.

Règles de dégradation

Une réserve d’espace minimale est vérifiée avant tout envoi : en dessous du seuil, les écritures sont refusées avec une erreur explicite, mais la lecture, la connexion et la suppression restent possibles — le service passe en lecture seule plutôt que de mourir. L’espace disponible est vérifié avant d’ouvrir une session d’envoi, pas seulement pendant, pour ne pas découvrir le problème après 30 Go transférés. Les fragments d’envois abandonnés et la corbeille sont purgés en priorité, et l’état de saturation est visible dans l’interface.

10Performance de transfert

Le §08 traite les requêtes Range sous l’angle de la compatibilité avec les gestionnaires de téléchargement. Cette section pose les exigences de débit, qui sont un objectif distinct et vérifiable.

Attente réaliste

Sur un téléchargement simple à une seule connexion, aucun gain n’est à espérer face à File Browser : les deux sont écrits en Go et servent leurs fichiers par le même chemin noyau. C’est déjà l’optimum. Le gain réel se situe ailleurs — dans le nombre de connexions que le client peut ouvrir, et dans les erreurs de configuration qu’on évite.

10.1Préserver le chemin sendfile

Sous Linux, http.ServeContent transfère les données du cache disque vers la socket réseau sans jamais les faire transiter par l’espace utilisateur. Toute couche qui transforme les octets annule cette optimisation. Trois règles en découlent :

  • Aucune compression sur les types déjà compressés — archives, images disque, médias. Compresser un .iso brûle du processeur sans rien gagner et supprime sendfile.
  • Aucun intergiciel de journalisation ou de métrique n’enveloppe le corps des réponses de contenu.
  • Content-Length toujours renseigné : pas d’encodage par fragments sur un fichier dont la taille est connue, sans quoi le client ne peut ni afficher une progression fiable, ni reprendre proprement.

10.2Le vrai levier : le nombre de connexions

Quand un serveur à haut débit délivre lentement, la cause est presque toujours un flux TCP unique sur une longue distance : son débit est plafonné par la latence et le taux de perte, pas par la bande passante disponible. Seize flux parallèles disposent de seize fenêtres de congestion indépendantes et remplissent un lien qu’un flux unique ne remplit jamais.

C’est la justification de performance — et non plus seulement d’ergonomie — des liens de partage sans état décrits au §08 : rien ne doit s’opposer à ce qu’un client ouvre autant de connexions qu’il le souhaite. Aucune limite de concurrence par jeton, aucune session à établir, aucun verrou côté serveur.

HTTP/2 dessert le transfert volumineux

Son multiplexage fait passer tous les flux dans une seule connexion TCP, donc une seule fenêtre de congestion, avec blocage en tête de file. Pour du téléchargement de masse, HTTP/1.1 avec plusieurs connexions fait mieux — c’est précisément pourquoi les gestionnaires de téléchargement y restent. HTTP/2 est utile sur l’origine application, pas sur l’origine contenu.

10.3Ce qui se règle en dehors du code

  • Pas de mise en tampon par le proxy inverse. Un proxy qui accumule la réponse avant de la relayer ajoute latence et mémoire pour rien. Traefik ne le fait pas par défaut, nginx si — à documenter.
  • Terminaison TLS. Son coût processeur devient le plafond au-delà de quelques Gb/s. Négligeable en dessous sur un processeur doté d’AES-NI.
  • Transfert de serveur à serveur. Le téléchargement depuis une URL (§3.2) contourne entièrement la connexion domestique de l’utilisateur : c’est le gain de débit le plus spectaculaire du produit, et il ne doit rien au serveur HTTP.

10.4Exigences vérifiables

Débit à une connexion
Doit atteindre la limite du disque ou du lien réseau, la plus basse des deux, sur un fichier plus volumineux que la mémoire disponible — afin de mesurer le disque et non le cache.
Montée en charge parallèle
Seize requêtes Range simultanées sur un même fichier doivent additionner leurs débits sans dégradation ni contention.
Consommation mémoire constante
Servir un fichier de 40 Go ne doit pas faire croître la mémoire du processus. Toute croissance signale une mise en tampon accidentelle — le symptôme le plus courant d’une régression de performance.
Sémantique Range
Couverte par des tests dédiés : plages ouvertes, plages suffixes, plages invalides, requêtes concurrentes sur un même fichier, reprise après coupure.

11.3Conventions transversales

Erreurs normalisées
application/problem+json (RFC 9457) partout, avec un code machine stable en plus du message lisible. Un client doit distinguer « permission refusée » de « chemin introuvable » sans analyser du texte.
Progression par SSE
Les tâches longues diffusent leur avancement en flux unidirectionnel. Le SSE traverse tous les proxies inverses sans configuration et se reconnecte seul. Un WebSocket ne se justifierait que pour de la collaboration temps réel, hors périmètre.
Versionnage strict
/api/v1 figé à la première publication. La spécification OpenAPI est générée depuis le code, jamais écrite à la main — sinon elle diverge en trois semaines.
Limitation de débit
Par jeton sur l’API, par IP sur les liens de partage.

12Choix technologiques

Recommandations tranchées, à valider. Chaque ligne indique la raison du choix plutôt que la liste des alternatives.

12.1Backend

Règle d’accueil des contributeurs

Ce qui compte pour un projet ouvert n’est pas la notoriété des outils mais la facilité d’entrée. Tout code généré est commité dans le dépôt : cloner puis go build suffit. Seul celui qui modifie une requête SQL régénère, et l’intégration continue vérifie que le généré correspond bien à la source.

Go 1.25+ Verrouillé
Binaire unique, excellente diffusion de flux, concurrence native. Le minimum est 1.25, pas 1.24 : os.Root apparaît bien en 1.24, mais Rename, RemoveAll et MkdirAll ne lui sont ajoutées qu’en 1.25 — sans elles, déplacer ou supprimer imposerait de résoudre les chemins à la main et de rouvrir la fenêtre de course que os.Root ferme. Corrigé après implémentation du §14 lot 1.2.
Routage : net/http standard Verrouillé
Le routage par motifs de la bibliothèque standard (Go 1.22+) couvre le besoin. Zéro dépendance sur le chemin critique des requêtes. On n’ajoute chi que si les intergiciels deviennent réellement complexes.
SQLite : modernc.org/sqlite Verrouillé
Implémentation en Go pur, donc CGO_ENABLED=0 : compilation croisée triviale et binaire réellement statique. Plus lente que la liaison cgo, mais notre charge est une poignée de requêtes de métadonnées — la distribution compte davantage. Mode WAL. Le pilote plus célèbre, mattn/go-sqlite3, impose cgo : incompatible avec la promesse d’un binaire unique multi-plateformes.
Accès données : sqlc Verrouillé
Génère du Go typé à partir de SQL écrit à la main. Pas d’ORM : les requêtes de résolution ACL sont trop spécifiques pour être bien servies par une abstraction. Pour un contributeur, l’effet est inverse de ce qu’on craint : il lit du SQL, universel, plutôt que le langage de requêtes propre à un ORM.
Migrations : goose embarqué Proposé
Fichiers SQL inclus via embed.FS, appliqués au démarrage. Aucun outil externe à installer pour mettre à jour. Le choix le moins engageant du lot : ce sont des fichiers SQL numérotés dans un dossier, et basculer vers golang-migrate ou atlas plus tard coûte une après-midi.
Uploads : sous-ensemble TUS maison Verrouillé
TUS est un protocole ouvert d’upload reprenable : le client ouvre une session, envoie des fragments successifs, et après une coupure interroge le serveur (HEAD) pour connaître la position atteinte et reprendre là plutôt que de tout recommencer. Suivre un protocole existant plutôt qu’en inventer un donne des clients tout faits dans la plupart des langages — cohérent avec « l’API est le produit ». On l’implémente soi-même plutôt que d’importer tusd, qui embarque ses propres backends de stockage alors que toute écriture doit passer par notre couche ACL ; on reste compatible sur le fil, donc les clients standard fonctionnent.
Tâches de fond : table jobs + goroutines Verrouillé
C’est le moteur des trois fonctionnalités longues de §3.2. Une requête HTTP ne peut pas durer trois heures. La persistance en base permet de survivre à un redémarrage (une mise à jour du binaire ne doit pas anéantir un téléchargement en cours), de diffuser l’avancement, d’annuler, et de limiter la concurrence — trois extractions simultanées saturent le disque du VPS. Sert aussi aux tâches périodiques : purge de corbeille, vignettes, index de recherche. Aucune dépendance externe : pas de Redis, pas de courtier de messages.
Journalisation : log/slog
Structuré, dans la bibliothèque standard.
Cryptographie
golang.org/x/crypto/argon2 pour les mots de passe, pquerna/otp pour le TOTP. Rien d’écrit à la main.

12.2Interface web

React + Vite Verrouillé
Svelte produirait un paquet plus léger — environ 80 Ko contre 150 Ko — mais sur une application servie par ton propre VPS et mise en cache dès la première visite, l’écart ne se ressent pas. Trois arguments l’emportent : un vivier de contributeurs bien plus large, une relecture des contributions faite avec autorité, et surtout un client mobile déjà en React Native — même paradigme, logique d’API partagée. La légèreté reste un principe du projet ; elle se joue sur le poids des dépendances qu’on ajoute, pas sur le framework.
shadcn/ui + Tailwind CSS Verrouillé
Material 3 Expressive a d’abord été retenu, puis abandonné. La bibliothèque possédait la cascade — ses styles vivaient dans des couches m3e.* qui l’emportaient sur tout — et sur un projet aussi jeune, chaque écart imposait un contournement de plus. Le rapport bénéfice/effort ne tenait pas.

À la place, shadcn/ui : non pas une dépendance mais des composants copiés dans src/components/ui, dont le dépôt est propriétaire et qu’il modifie à volonté. Ils s’appuient sur les primitives Radix pour le comportement accessible et sur Tailwind CSS pour le style — ici il n’y a plus de seconde bibliothèque avec qui se disputer la cascade, donc plus de guerre de couches. Icônes : @phosphor-icons/react (trait simple partout, duotone au sidebar). Coût : un CSS compressé modeste (~7 Ko) ; le JavaScript, lui, a grossi avec Radix, Phosphor et les toasts — acceptable pour une application auto-hébergée mise en cache, et à surveiller. Détail dans la conception de l’interface.
Palette en jetons sémantiques Verrouillé
Une quinzaine de jetons — background, primary, muted, destructive… — définis une fois en clair et une fois en sombre, tous dérivés à la main du vert pin #2F5D50 et du laiton #8E6528. Le mode sombre suit le système : personne n’ouvre un gestionnaire de fichiers pour choisir un thème.

Cela remplace la génération de rampes tonales de treize teintes que réclamait Material — toute une chaîne d’outillage pour éviter de choisir seize couleurs à la main. Une couleur qu’on peut lire est une couleur qu’on peut corriger : les valeurs sont de simples hexadécimaux dans index.css.
Discipline de structure
Les composants réutilisables vivent dans src/components/ui, copiés depuis le registre shadcn pour qu’un futur shadcn add reste compatible ; les écrans les composent avec des utilitaires Tailwind. Un motif qui se répète devient un composant, jamais un bloc de balisage recopié. À inscrire dans le CONTRIBUTING.md.
TanStack Virtual Verrouillé
Un dossier de dix mille fichiers, c’est dix mille éléments dans le DOM : défilement saccadé, navigateur à genoux. La virtualisation ne construit que la trentaine de lignes réellement visibles et les recycle au défilement. Très concret ici — un dossier d’installation de jeu contient facilement des milliers de fichiers. Environ 5 Ko.
Client TUS écrit à la main Proposé
Environ deux cents lignes. Les bibliothèques d’upload clés en main type Uppy pèsent bien plus que la fonctionnalité rendue.
Client d’API généré Proposé
Types TypeScript produits depuis la spécification OpenAPI, partagés entre l’interface web et le client mobile. Une seule source de vérité pour le contrat.

12.3Distribution & qualité

Nommage Verrouillé
Module Go github.com/<compte>/zefile, binaire zefile, image Docker zefile, préfixe de jetons zefile_live_. Fixé avant la première ligne de code : renommer un module Go après publication oblige tous les consommateurs à modifier leurs imports.
Binaire unique
Interface web embarquée par embed.FS. Publication multi-plateformes via GoReleaser.
Docker minimal
Image scratch ou distroless, multi-architecture. Rien d’autre que le binaire.
Service direct depuis Go
http.ServeContent gère correctement Range et s’appuie sur sendfile sous Linux : les performances sont déjà là. Le déchargement vers nginx (X-Accel-Redirect) reste une optimisation facultative, pas un prérequis.
Licence Apache-2.0 Verrouillé
Permissive : usage commercial, modification, redistribution et fermeture des dérivés sont autorisés sans contrepartie. Retenue plutôt que MIT pour sa concession de brevet explicite — un contributeur ne peut pas céder du code puis attaquer les utilisateurs sur un brevet le couvrant — et pour rester dans le même régime que File Browser, ce qui évite toute friction si l’on reprend un fragment ou une idée d’implémentation.
Chaîne de sécurité dès le premier jour
govulncheck et gosec en intégration continue, mises à jour de dépendances automatisées, SECURITY.md et procédure de divulgation publiés avant la première version. C’est la leçon directe de File Browser.
Tests
Bibliothèque standard. Tests d’intégration sur une vraie base SQLite et un système de fichiers temporaire. Couverture prioritaire : résolution ACL, normalisation des chemins, sémantique de Range, reprise d’upload.

12.4Organisation du dépôt

Dépôt unique, frontend et backend ensemble. Ce n’est pas un choix de confort : le binaire embarque l’interface via embed.FS, donc la compilation Go dépend des fichiers produits par Vite. Deux dépôts imposeraient de synchroniser deux versions pour un artefact final unique. S’y ajoute le contrat d’API partagé — spec OpenAPI générée depuis le Go, types TypeScript générés depuis la spec.

zefile/
├── cmd/zefile/          point d'entrée
├── internal/
│   ├── storage/         VFS, os.Root, application des ACL
│   ├── auth/            sessions, jetons, TOTP
│   ├── acl/             résolution des permissions
│   ├── share/           liens publics
│   ├── jobs/            file de tâches
│   ├── api/             handlers, origine app
│   ├── content/         origine contenu
│   └── db/              sqlc généré + migrations
├── web/                 React + Vite + Tailwind (pnpm)
├── api/openapi.yaml     généré depuis le code
├── deploy/              compose, template Dokploy
├── docs/
└── Makefile

Le répertoire internal/ n’est pas décoratif : Go interdit son importation depuis l’extérieur du module, ce qui laisse toute liberté de remanier ces paquets sans rien casser chez personne. Seule l’API HTTP constitue un contrat public.

Client mobile hors dépôt
Cycle de publication distinct et contraintes de magasin d’applications. Il consomme le client TypeScript généré, versionné avec l’API.
web/dist non versionné Verrouillé
Trois raisons, par ordre de gravité. Relecture : du code compilé n’est pas relisable — une contribution dont le dist ne correspond pas à ses sources ferait entrer du JavaScript invisible en revue, ce qu’un outil à vocation sécurisée ne peut pas se permettre. Conflits : chaque contributeur qui construit régénère des empreintes de fichiers différentes, donc chaque proposition porte un diff massif qui entre en collision avec toutes les autres. Lisibilité de l’historique : les vrais changements se noient dans le bruit. Contrepartie assumée : pas d’installation par go install en une commande — l’image Docker et les binaires publiés couvrent la quasi-totalité des cas, et compiler depuis les sources demande Node, ce qui est attendu pour un projet doté d’une interface web. Les seuls artefacts distribués sont ceux que l’intégration continue produit à partir des sources.

13Déploiement

La facilité d’installation est un critère de conception, pas une phase de documentation. File Browser doit une bonne part de son adoption à son binaire unique : Zefile doit être au moins aussi simple à mettre en service.

13.1Un conteneur, un port, deux hôtes

La séparation d’origine (§4.1) est le seul surcoût de déploiement par rapport à File Browser. Il reste modeste : le binaire route selon l’en-tête Host, donc un seul conteneur et un seul port desservent les deux domaines. Le coût réel se limite à un enregistrement DNS supplémentaire et à un second domaine déclaré dans le proxy inverse.

13.2Données et configuration strictement séparées

Règle de démarrage

Si la base SQLite se trouve à l’intérieur de l’arborescence parcourue, les utilisateurs peuvent la lister, la télécharger — hachés de mots de passe compris — voire la supprimer. Zefile refuse de démarrer si le répertoire de configuration est situé dans la racine de stockage.

La corbeille et les fragments d’upload en cours doivent en revanche résider sur le même système de fichiers que les données, faute de quoi supprimer un fichier de 40 Go déclenche une copie complète au lieu d’un simple renommage. Ils vivent donc en répertoires cachés à l’intérieur de la racine, exclus des listings.

13.3Composition de référence

services:
  zefile:
    image: ghcr.io/<compte>/zefile:latest
    restart: unless-stopped
    environment:
      ZEFILE_APP_URL:     https://zefile.exemple.tld
      ZEFILE_CONTENT_URL: https://dl.exemple.tld
      ZEFILE_DATA_DIR:    /data
      ZEFILE_CONFIG_DIR:  /config
      PUID: 1000
      PGID: 1000
    volumes:
      - /mnt/stockage:/data      # disque de l'hôte, pas un volume Docker
      - zefile-config:/config
    ports:
      - "8080:8080"

volumes:
  zefile-config:

Le montage direct d’un répertoire de l’hôte donne accès à la totalité du disque du VPS, ou à un disque supplémentaire monté ailleurs — pas à un volume Docker cloisonné.

13.4Mode origine unique

Une partie des utilisateurs ne configurera jamais le second domaine. Plutôt que de les laisser désactiver la protection sans le savoir, un mode explicite durcit automatiquement le service :

  • Tout contenu utilisateur est servi en Content-Disposition: attachment avec un en-tête Content-Security-Policy: sandbox
  • L’affichage en ligne se limite aux types que le navigateur isole lui-même : images matricielles, vidéo, audio, PDF
  • Le SVG est exclu de l’affichage en ligne — c’est une image capable d’exécuter du script, et c’est le piège classique
  • Avertissement au démarrage dans les journaux

Les aperçus restent fonctionnels, sur une surface réduite. Ce n’est pas l’équivalent des deux origines, mais c’est explicite et documenté.

13.5Ce qui décide si l’installation est réellement facile

PUID / PGID
Le conteneur s’exécute sans privilèges, mais un répertoire monté depuis l’hôte appartient à un utilisateur donné. Sans ces variables, les envois échouent sur une erreur de permission incompréhensible — le tout premier obstacle rencontré en auto-hébergement.
Aucune configuration initiale
Aucun fichier à rédiger avant le premier lancement. Zefile génère un lien d’installation à usage unique, affiché dans les journaux, qui sert à créer le compte administrateur. Pas d’identifiants par défaut.
Images multi-architectures
Beaucoup de VPS économiques et de machines domestiques tournent sur ARM. Publication sur GHCR pour amd64 et arm64.
Sonde de santé
Endpoint dédié, pour que l’orchestrateur sache si le service répond réellement.
Aucun réglage de proxy inverse
Effet secondaire du choix TUS : les envois étant fragmentés, aucune requête ne transporte 40 Go. On échappe aux limites de taille de corps et aux délais d’expiration qui sont la plaie des serveurs de fichiers classiques. Fonctionne derrière Traefik sans configuration particulière.
Base de données sur disque local
Le répertoire de configuration ne doit pas résider sur un partage réseau : le verrouillage SQLite y est peu fiable. Seules les données peuvent l’être.

Un template Dokploy est publiable dès la première version : leur catalogue est un dépôt ouvert aux contributions.

13.6Sauvegarde, restauration, déménagement

Attente de base en auto-hébergement, et elle comporte un piège : copier le fichier SQLite pendant que le service tourne produit une sauvegarde corrompue. Une écriture peut être en cours, et le journal WAL vit dans des fichiers annexes. C’est l’erreur classique, et elle ne se découvre qu’au moment de restaurer.

zefile backup
Produit un instantané cohérent de la base à chaud, par VACUUM INTO — sûr sans interrompre le service. Sauvegarde les métadonnées seules : ACL, comptes, partages, corbeille, propriété. Les fichiers eux-mêmes relèvent des outils habituels (rsync, instantanés du système de fichiers), et il n’y a aucune raison de les dupliquer dans un format propriétaire.
zefile restore
Restaure une sauvegarde, puis signale les divergences : entrées ACL et de propriété pointant vers des chemins absents, éléments de corbeille disparus. Métadonnées et fichiers étant sauvegardés séparément, ils peuvent dater de moments différents — l’outil le dit plutôt que de laisser une incohérence silencieuse.
Déménagement de serveur
Copier les données, restaurer la base, ajuster les deux URL d’origine. Documenté comme procédure, testé comme un scénario à part entière — c’est ce que feront les gens qui migrent depuis File Browser.
Sauvegarde avant migration de schéma
Les migrations s’appliquent au démarrage ; un instantané est pris automatiquement juste avant. Sur une machine auto-hébergée, personne n’a de plan de retour arrière — autant le fournir.

14Découpage

Ordonné par dépendances techniques, sans échéance. Chaque phase se termine sur quelque chose d’utilisable. Le découpage détaillé, lot par lot et avec les critères d’achèvement, vit dans un document séparé : roadmap d’implémentation.

1
Fondations
Couche de stockage avec os.Root, SQLite, sessions révocables, moteur ACL, API v1 sur les opérations fichiers, upload et download reprenables. Interface minimale mais fonctionnelle. La phase la plus longue et la moins gratifiante ; celle qui décide de la qualité de tout le reste.

Invitations, gestion des comptes, interface d’ACL, corbeille.
3

Liens, origine de contenu séparée, journal d’accès, jetons d’API. Les partages sont une projection du modèle ACL : les construire avant qu’il soit éprouvé, c’est se condamner à les réécrire.
4
Confort
Aperçus, vignettes, recherche FTS, tâches de fond — téléchargement depuis URL, extraction, empreintes.
5
Finition & ouverture
Interface aboutie, OpenAPI publiée, image Docker, outil de migration depuis File Browser, adaptation du client mobile existant.
→
Ensuite
WebDAV, OIDC, S3, versions de fichiers.

15Questions ouvertes

Aucune question ouverte

La conception est close : périmètre, architecture, modèle de données, sécurité, API, technologies, organisation du dépôt et déploiement sont arrêtés. L’implémentation peut commencer.

Trois lignes restent marquées « Proposé » en §12 — l’outil de migration, le client TUS et la génération du client d’API. Ce ne sont pas des questions ouvertes mais des détails d’implémentation sans effet sur l’architecture ; ils se trancheront en les écrivant.

Les points volontairement reportés — WebDAV, OIDC, S3, versions de fichiers — figurent en §3.3 avec leurs contraintes de conception, pour qu’aucun ne devienne impossible.
