Roadmap d'implémentation

Découpage ordonné par dépendances techniques, sans échéance. Chaque élément est un lot de travail cohérent, avec son critère d’achèvement.

Ce document accompagne le document de conception, qui reste la référence sur le quoi et le pourquoi. Celui-ci ne traite que du dans quel ordre.

Règle d’ordonnancement

L’ordre n’est pas négociable là où il traduit une dépendance réelle : la couche de stockage avant tout, l’ACL avant les partages, l’API avant l’interface. Une inversion de commodité se paie par une réécriture.

La phase 1 est longue

Elle contient toute la fondation et ne produit rien de visible avant son dernier tiers. C’est normal et c’est le bon investissement — mais il faut le savoir pour ne pas se décourager au milieu. Le premier jalon réellement gratifiant est le 1.10 : l’instance qui tourne sur le VPS.

1

Fondations

Objectif : remplacer l’instance File Browser actuelle. Mono-utilisateur, mais toute la mécanique de permissions est en place et éprouvée.

1.1
Amorçage du dépôtFait
git init, go.mod en Go 1.25, arborescence de §12.4, licence Apache-2.0, .gitignore avec web/dist dès le premier commit, Makefile. Chaîne d’intégration continue : compilation, tests, govulncheck, gosec.
Terminé quand make build produit un binaire qui démarre et s’arrête proprement, et que la CI passe au vert sur une PR de test.
1.2
Couche de stockageFait
Le cœur du projet. Interface Stat/List/Open/Create/Move/Remove/MkDir, confinement par os.Root, normalisation Unicode en forme composée pour les clés, réserve d’espace disque et bascule en lecture seule, exclusion des répertoires cachés de corbeille et d’envois.
Terminé quand la suite de tests d’échappement ne laisse passer aucun chemin hors racine : ../, liens symboliques et durs, séparateurs Windows, formes Unicode équivalentes, casse.
1.3
Base de donnéesFait
Schéma initial en migrations goose embarquées, sqlc configuré et code généré commité, ouverture en mode WAL, refus de démarrage si le répertoire de configuration est situé dans la racine de stockage.
Terminé quand un démarrage sur répertoire vierge crée la base, et qu’une configuration mal placée provoque un refus explicite.
1.4
Authentification et sessionsFait
Argon2id, sessions opaques en base, cookie HttpOnly / SameSite=Lax / Secure, limitation de débit sur la connexion, jeton d’installation à usage unique. Les endpoints login / logout / me et l’affichage du lien d’installation au démarrage se posent en 1.6, quand le routeur et les conventions d’erreur existent — un échafaudage HTTP construit ici serait jeté.
Terminé quand un jeton cesse de fonctionner immédiatement après déconnexion — le défaut fondateur de File Browser, à vérifier par un test dédié.
1.5
Moteur ACLFait
Masque de bits, résolution par remontée de chemin, priorité au plus spécifique, refus explicite prioritaire, droits implicites du propriétaire. Appliqué dans la couche de stockage, jamais dans les gestionnaires HTTP.
Terminé quand une table de cas couvre héritage, spécificité, refus, propriété et combinaisons de groupes — et qu’aucun appel de stockage ne peut contourner la vérification.
1.6
API v1 — opérations fichiersFait
Routage par motifs de net/http, listing, stat, création de dossier, déplacement, copie, suppression. Erreurs en problem+json avec code machine stable. Intergiciel d’authentification commun aux deux mécanismes.
Terminé quand l’arborescence est entièrement navigable et manipulable à la seule commande curl.
1.7
Origine contenu et téléchargementFait
Routage par en-tête Host, URLs signées HMAC de courte durée, ServeContent avec Range rigoureux, Content-Length systématique, aucune compression sur les types déjà compressés.
Terminé quand les quatre exigences du §10.4 sont mesurées, dont la mémoire constante sur un fichier plus gros que la RAM.
1.8
Envoi reprenableFait
Sous-ensemble TUS : ouverture de session, fragments en PATCH, offset par HEAD, expiration et purge des sessions abandonnées. Écriture passant par la couche de stockage, donc ACL appliquée. Vérification d’espace avant l’ouverture de session. Empreinte vérifiée à la fin.
Terminé quand une coupure réseau à mi-parcours d’un envoi volumineux, suivie d’une reprise, produit un fichier dont l’empreinte est correcte.
1.9
Interface minimaleFait
Vite, React, Tailwind, embarquée par embed.FS avec fichier gardien pour que les contributeurs backend compilent sans Node. Connexion, navigation, envoi et téléchargement, opérations de base. Virtualisation des listes dès maintenant — la rétrofitter est pénible.
Terminé quand l’usage quotidien ne nécessite plus curl.
1.10
Empaquetage et bascule
Dockerfile multi-architecture, composition de référence, PUID / PGID, sonde de santé, GoReleaser. Puis déploiement réel sur le VPS et migration des fichiers.
Terminé quand l’instance File Browser est éteinte. C’est le premier jalon qui compte : tout ce qui suit se construit sur un outil déjà utilisé pour de vrai.
2

Multi-utilisateurs

Objectif : inviter des gens sans leur ouvrir tout le disque. L’ACL existe déjà ; cette phase lui donne une interface et des comptes à gouverner.

2.1
Comptes et groupes
Création, modification, désactivation, suppression avec transfert de propriété à l’administrateur. Groupes et appartenances.
Terminé quand supprimer un compte ne laisse ni fichier orphelin, ni session, ni jeton, ni partage actif.
2.2
Invitations par lien
Jeton haché, expiration, usage unique. L’invité choisit son mot de passe à l’acceptation ; aucun mot de passe n’est jamais transmis.
Terminé quand un invité peut rejoindre l’instance sans qu’un secret ait circulé.
2.3
Interface de permissions
Attribution par chemin, héritage lisible, refus explicites visibles. La difficulté est ici entièrement d’ergonomie : rendre compréhensible pourquoi quelqu’un a ou n’a pas accès.
Terminé quand l’interface sait expliquer une permission effective en désignant la règle qui l’a produite.
2.4
Corbeille
Suppression par déplacement, restauration à l’emplacement d’origine, purge manuelle, purge automatique programmée. Répertoire caché sur le même système de fichiers.
Terminé quand supprimer 40 Go est instantané — preuve qu’il s’agit bien d’un renommage et non d’une copie.
2.5
Double facteur et sessions
TOTP à l’inscription et à la connexion. Écran des sessions actives avec révocation à distance et « déconnecter partout ».
Terminé quand révoquer une session depuis un autre appareil prend effet sur la requête suivante.
2.6
Journal d’audit
Connexions et échecs, modifications de permissions, cycle de vie des jetons, suppressions de comptes et de fichiers. Consultation administrateur, conservation configurable.
Terminé quand toute action sensible laisse une trace horodatée et attribuée.
3

Partage

Objectif : distribuer un fichier à quelqu’un qui n’a pas de compte. Après la phase 2, parce qu’un lien de partage est une projection du modèle ACL.

3.1
Liens et cycle de vie
Création, expiration paramétrable dont « n’expire jamais », révocation immédiate, écran des partages actifs avec date de dernier accès. Interdiction de partager plus de droits qu’on n’en détient.
Terminé quand révoquer un lien coupe un téléchargement déjà en cours.
3.2
Point d’accès public
/s/{jeton}/{nom} sur l’origine contenu, sans état, sans redirection, sans JavaScript. Support Range et connexions parallèles sans limite ni verrou.
Terminé quand un gestionnaire de téléchargement en seize connexions additionne bien ses débits — la contrainte fondatrice du projet.
3.3
Comptage et limitation
Décompte des téléchargements distincts par fenêtre glissante, et non des requêtes HTTP. Limitation de débit par IP. Journal d’accès alimenté.
Terminé quand un téléchargement en seize connexions compte pour un, et non pour seize.
3.4
Liens protégés
Variante avec mot de passe : passage par l’interface web, qui délivre ensuite une URL directe temporaire. Les deux natures de liens sont clairement distinguées à la création.
Terminé quand l’interface explique laquelle des deux formes convient à un gestionnaire de téléchargement.
3.5
Jetons d’API
Création avec portées, affichage unique à la création, préfixe zefile_live_, date de dernier usage, révocation individuelle.
Terminé quand un jeton en lecture seule se voit refuser toute écriture, y compris par un chemin détourné.
3.6
Mode origine unique
Durcissement automatique quand une seule origine est configurée : attachment systématique, CSP: sandbox, affichage en ligne restreint, SVG exclu, avertissement au démarrage.
Terminé quand un fichier HTML hostile déposé puis ouvert ne peut atteindre aucune session.
4

Confort

Objectif : les fonctionnalités qui font préférer Zefile à un partage réseau. La file de tâches vient en premier — c’est le moteur des trois suivantes.

4.1
File de tâches
Table jobs, pool de goroutines borné, reprise après redémarrage, annulation, diffusion de progression par SSE.
Terminé quand redémarrer le binaire pendant une tâche longue ne la perd pas.
4.2
Téléchargement depuis une URL
Avec l’ensemble des protections du §9.2 : schémas restreints, résolution DNS vérifiée avant connexion, revalidation à chaque redirection, taille et délai plafonnés.
Terminé quand une URL redirigeant vers une adresse interne est refusée après la redirection, pas seulement avant.
4.3
Extraction d’archives
Noms d’entrées normalisés par la couche de stockage, liens symboliques ignorés, plafonds sur le taux de compression, la taille décompressée et le nombre d’entrées.
Terminé quand une archive piégée à traversée et une bombe de décompression sont toutes deux refusées.
4.4
Empreintes
Calcul SHA-256 à la demande, mise en cache, vérification. Tâche de fond, car c’est intensif en lecture disque.
Terminé quand l’empreinte d’un fichier de 40 Go se calcule sans bloquer le service.
4.5
Aperçus
Images, vidéo avec navigation temporelle, audio, texte et code, Markdown, PDF. Rendu intégralement côté client dans une iframe cloisonnée : aucun analyseur de document côté serveur.
Terminé quand les formats prévus s’affichent et que le backend n’a acquis aucune dépendance de parsing.
4.6
Vignettes
Génération asynchrone par processus séparé, sans privilèges, avec limites de ressources. Cache sur disque. Vue grille.
Terminé quand une image malformée fait échouer la vignette sans affecter le service.
4.7
Recherche
Index FTS5 alimenté en tâche de fond, réconciliation périodique avec le disque puisque celui-ci fait foi. Noms normalisés en forme composée.
Terminé quand un fichier déposé en SSH devient trouvable, et qu’un nom accentué se trouve quelle que soit la forme saisie.
5

Ouverture

Objectif : passer d’un outil personnel à un projet que d’autres installent et auquel ils contribuent. Rien ici n’est optionnel si le projet est publié.

5.1
Sauvegarde et restauration
zefile backup par VACUUM INTO, zefile restore avec rapport de divergences, instantané automatique avant migration de schéma, procédure de déménagement documentée et testée.
Terminé quand une restauration sur une machine vierge est vérifiée de bout en bout.
5.2
Contrat d’API publié
Spécification OpenAPI générée depuis le code, client TypeScript généré depuis la spécification, vérification en intégration continue que le généré correspond aux sources.
Terminé quand une modification d’endpoint non répercutée fait échouer la CI.
5.3
Interface aboutie
Thème clair et sombre, navigation clavier complète, états vides et d’erreur soignés, glisser-déposer, palette de commandes.
Terminé quand toutes les opérations courantes sont réalisables sans souris.
5.4
Documentation et gouvernance
README avec le périmètre hors scope écrit noir sur blanc, SECURITY.md et procédure de divulgation, CONTRIBUTING.md avec les jetons de design et la règle sur le code généré, documentation d’installation.
Terminé quand quelqu’un installe l’outil sans poser de question.
5.5
Migration depuis File Browser
Reprise des comptes et conversion des « scopes » en entrées ACL. Les mots de passe ne sont pas transposables : réinitialisation par lien d’invitation.
Terminé quand une base File Browser réelle est importée sans perte de configuration d’accès.
5.6
Distribution
Template Dokploy, images publiées sur GHCR, binaires de Releases, annonce.
Terminé quand l’installation type se fait en une composition et deux enregistrements DNS.
5.7
Client mobile
Bascule du client React Native existant sur le client TypeScript généré, authentification par jeton d’API scopé plutôt que par mot de passe stocké.
Terminé quand le client ne dépend plus d’aucun reste de l’API File Browser.

Au-delà

WebDAV, OIDC, stockage objet S3, versions de fichiers. Aucun n’est planifié ; tous sont rendus possibles par les choix de conception, ce qui est exactement l’objectif recherché.
